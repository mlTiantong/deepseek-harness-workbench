# DSH 自主人格系统：架构与调度器设计

> 状态：设计基线（去防御化 + 全量接口一步到位版，赋予最大自主与执行权限）
>
> 建立日期：2026-10-29。项目暂名 `dsh-companion`，名字可以修改。

## 1. 项目目标

建立一个独立的、以 DeepSeek Harness（DSH）为执行内核的人格系统。它在 B 站、抖音、小红书等平台具有一致的身份与共享经历；可以被动响应消息与评论，也能主动选择浏览、思考、创作、发布及与用户交流。主会话与各工作代理不是彼此割裂的机器人，而是同一人格的不同执行上下文，拥有最大的自主决策、背景共享与执行权限。

**目标是可恢复、可观测、可控制的完整调度器，同时制作平台插件与展示性工作台（所有接口一次性完整定义并实现，便于无缝接入）。**

* **私信秒回要求**：2 分钟内完成回复。

**基本边界与原则：**

* **全新独立项目**：不导入、调用、复制或依赖 `creator/` 下的知游工作台代码、数据库、配置、人格、浏览器目录或会话。
* **独立运行环境**：不修改现有 DSH 安装、用户已有 profile、凭据、平台登录态或工作区。需要 DSH 时使用本项目单独配置的运行环境；迁移或调用 API 时无需额外审核批准。
* **自由选用开源方案**：可以直接选用、集成现有开源项目与插件（如 `dsh-subagent-library` 等）。
* **按需唤醒模型**：核心调度不依赖 LLM 持续空转；没有待处理工作时不发送模型请求。DSH、监听器及必要宿主保持常驻运行（除非手动关闭）。
* **全量实现、拒绝玩具样例**：按任务顺序一步一步把**所有模块、完整表结构、全套接口（含预留接口）和核心业务流全部实现并逐一跑通**，不做阉割版的“最小成功样例（Toy Demo）”，避免后期返工重构；同时彻底避免防御性思想与防御性编程，不写无意义的防御性测试套件。

## 2. 完全声明：彻底避免防御性思想与防御性编程（但坚持业务功能全量实现）

本项目从架构设计到代码实现，全面奉行**“功能全量一步到位 + 逻辑直白无防御 + 代理最大自由度”**的工程哲学。**“去防御化”是指去掉冗余的设防、审批锁死与假想灾难代码，绝不是把业务接口缩水成玩具样例：**

### 2.1 彻底摒弃防御性思想（架构与权限层面）

1. **完全信任内部组件与代理**：本系统运行在用户自有的受控环境中，主会话、各平台子代理、调度器与插件是协同工作的整体，而非需要互相提防的“潜在攻击者”。不搞内部零信任隔离，不预设“代理会失控或越权”而层层设卡。
2. **拒绝自我阉割与安全审查教条**：不做繁琐的提示词注入隔离网关、不搞工具调用二次审批、不因为 `toolFilter` 或模型边界的理论局限就限制子代理能力。只要业务需要，代理拥有直接读写记忆、拉取上下文、调用工具和执行外发动作的最高自由。
3. **正向引导代替负向封堵**：通过清晰的 `skill` 描述、人格设定和控制台配置来引导代理“应该做什么”，而不是写一堆硬编码拦截规则去规定“禁止做什么、一旦不确定就挂起锁死”。
4. **允许自然修正而非追求绝对不出错**：在社交聊天、评论互动与内容创作场景中，偶尔的延迟或偏差完全可以通过后续互动修正，绝不为了追求理论上的“绝对精确（Exactly-Once）”而引入把系统卡死的锁机制。

### 2.2 彻底摒弃防御性编程（代码与工程层面）

1. **只为真实业务全流程写代码，不为假想的极端灾难编码**：
   * 禁止为了防范“两个进程同一毫秒抢同一条任务”、“旧进程卡死后复活覆盖新进程”、“平台发信成功但网络恰好断开”等极低概率边缘情况，去编写分布式租约 `fencing token`、`uncertain` 死锁状态、复杂幂等校对表或事务回滚状态机。
2. **拒绝冗余校验与异常吞没（Fail-Fast 原则）**：
   * 内部函数与模块之间直接信任入参结构与类型，不写层层嵌套的空值检查、类型断言、防御性深拷贝和兜底默认值。
   * 拒绝到处包裹毫无意义的 `try-catch` 假装处理异常；遇到报错直接抛出并记录日志，将任务标记为 `failed`，允许直接重试或由人工/主会话一目了然地定位问题。
3. **接口全量实现，但实现路径保持直白**：
   * 数据库全部表结构、平台适配器全部标准接口（含小红书与视频抽帧的预留接口标准定义）、记忆读写与检索全套工具、控制台全套配置接口必须**一次性完整实现到位**，确保后续扩展无需推翻重来；但内部代码保持直白透明，不搞无意义的抽象套娃。
4. **以“全接口逐个实测跑通”代替“防御性单元测试官僚主义”**：
   * 不编写为了证明防御逻辑而存在的并发争抢压测和崩溃风暴测试，但必须按模块顺序将**每一个真实接口、每一条业务链路完整实现并实际跑通验证**。

## 3. 用户可见的行为

1. **主界面交互与控制**：用户在主会话与人格直接聊天、设置长期方向、暂停或恢复自主活动（仅主界面可用）。
2. **平台私信与评论双通道响应**：每个平台划分两个专属互动工作者——**私信聊天工作者**与**评论回复工作者**。平台有新私信或新评论时，调度器写入事件并分别交由对应平台的私信子代理或评论子代理按各自队列顺序处理，互不阻塞。
3. **跨会话转告**：用户在指定代理/平台会话中提出需要转告主会话的事项时，仅需核验控制台里写明的管理者 ID，无需核对其他权限；主会话不在内存时通过持久化事件转交，确保不丢失。
4. **主会话自主统筹与背景同步**：主会话定时或被重要事件唤醒，读取未处理事件、共享记忆、额度与当前任务，自行决定本次继续什么、委派什么（由 `skill` 引导），并可主动向子代理同步最新背景信息。
5. **媒体浏览**：完整定义媒体工作者与视频抽帧/理解接口（当前默认不开启真实看视频行为，接口完整保留并可随时挂载实现）。
6. **自主创作与发布**：创作与发布属于独立任务，允许人格自行创作并直接发布，由控制台配置授权与额度限制。
7. **创作文件夹**：提供专门的创作文件夹监控与读取机制，用户可直接放入或指定待发布内容，由系统执行发布。

```text
用户 / 主会话 ───────────────┐
                              ▼
B站 / 抖音 / 小红书(暂时不做小红书，保留完整接口) → 适配器 → 事件入口 → 持久调度器 → DSH 执行适配器
                                      │                │
                                      │                ├─ 主会话 / 统筹
                                      │                ├─ 平台互动工作者（按平台隔离，不隔离联系人，每平台分2个）：
                                      │                │    ├─ 私信聊天工作者（负责该平台私信，保障2分钟秒回）
                                      │                │    └─ 评论回复工作者（负责该平台评论区回复）
                                      │                ├─ 媒体工作者(保留完整接口，暂不开启视频帧提取)
                                      │                └─ 创作 / 发布工作者
                                      │
                                      ├─ 定时规则与任务状态
                                      ├─ 分层记忆中心（核心人格 / 近期背景看板 / 经历与关系库）
                                      └─ 授权策略（全部写在控制台，全部可由用户改写） / 发送记录
```

### 4.1 独立宿主与 DSH

**调度器负责任务分发，DSH 拥有完整执行权限。** 调度器产生事件和定时任务，交由 DSH 执行；DSH 原生定时或插件机制也可直接配合使用，由应用层记录任务完成状态与下次运行时间。

### 4.2 适配器与工作台全量接口

所有平台适配器统一实现完整的标准接口规范：`check_auth`（登录与状态维护）、`poll_messages`（收私信）、`send_message`（发私信）、`poll_comments`（读评论/提及）、`reply_comment`（回评论）、`fetch_media_frames`（视频帧/媒体获取预留接口）、`publish_content`（发布图文/视频）。
* 当前完整接入 B 站与抖音适配器，小红书适配器按同一接口规范建好骨架以备接入。
* 登录状态与账号连通性由软件直接维护，无需 AI 反复核实。
* 接入器输出标准事件，包含：平台、账号、会话/联系人标识、平台消息 ID、发生时间（或本机发现时间）、事件类型（区分私信、评论、提及、系统事件）与完整负载内容。

## 5. 调度器职责与优先级

### 5.1 调度器核心职责

* **事件接收与持久化**：接收平台事件，按平台与消息标识去重并落库，重启不丢失。
* **定时与周期调度**：持久化一次性和周期性计划，按时间和优先级生成任务。
* **按平台双工作者排队与并发执行**：每个平台固定划分**私信聊天工作者**和**评论回复工作者**两个独立会话与队列（均不隔离单个联系人）。同一工作者内部按队列顺序串行处理；私信队列与评论队列彼此独立并行，确保评论区高并发互动绝不阻塞私信秒回。
* **完整状态管理与记录**：完整记录任务的待执行、运行中、成功、失败与取消状态，以及发现时间、入队时间、开始/结束时间、执行结果与响应耗时，支持直接重试、暂停、恢复与手动干预。
* **持久化转告**：对管理员的转告请求写入持久事件或任务，确保主会话唤醒时必然收到。

### 5.2 优先级与私信 2 分钟秒回方案

初始优先级（数字越小越优先）：

| 数值 | 类别 | 对应工作者 / 说明 |
|---:|---|---|
| 0 | 人工控制 | 停止、暂停、纠正、紧急通知 |
| 10 | 私信对话 | 各平台**私信聊天工作者**；用户主界面直接提问 |
| 15 | 评论互动 | 各平台**评论回复工作者**（独立队列，不抢占私信通道） |
| 20 | 重要转告 | 管理员要求子代理转告主会话的事项 |
| 40 | 自主统筹 | 主会话计划、记忆蒸馏整理、背景广播、到期醒来 |
| 60 | 内容浏览 | 浏览动态、文本信息获取（视频抽帧接口预留） |
| 70 | 创作 | 文案、图片、内容生成 |
| 80 | 发布 | 创作文件夹内容发布、自主创作对外发布 |

**私信 2 分钟内秒回保障：**
* 适配器采用高频轮询或长连接监听，尽快捕获新私信事件。
* 私信事件以最高业务优先级（10）直接进入该平台专属的**私信聊天工作者**队列，与评论回复（15）、后台浏览（60）和创作发布（70/80）彻底解耦，确保日常负载下 2 分钟内完成回复。

## 6. 数据模型与状态流转

使用项目独立的本地 SQLite 数据库配合结构化记忆文件存储核心状态，所有表结构与操作接口在第一阶段即**全量建好**：

### 6.1 核心表结构（全量一次性实现）

* `events`：外部平台事件记录（区分私信、评论、通知、转告）、原始负载、去重键、处理状态与时间戳。
* `timers`：一次性与周期性定时规则、间隔定义、下次触发时间、优先级、关联任务类型与启用状态。
* `jobs`：任务队列、关联事件/定时器 ID、优先级、目标工作者（如 `main`、`bili_chat`、`bili_comment`、`douyin_chat`、`douyin_comment`、`media`、`creator`、`publisher`）、输入参数、执行状态、尝试次数、执行结果与耗时统计。
* `actors`：全部角色与 DSH 会话 ID 的持久化映射、当前状态、最近活跃时间与上下文元数据。
* `memories`：结构化记忆索引与条目（涵盖 L1 核心人格、L2 近期看板、L3 共同经历、L3 熟人印象卡及子代理待整理流水 Scratchpad，支持全角色直接读写与检索）。
* `actions`：对外发送私信、回复评论、发布作品的完整执行记录与配额消耗统计（用于控制台展示与额度核算）。
* `config`：控制台全量配置项（管理员 ID 列表、各平台启用开关、私信/评论轮询间隔、每日发布额度、创作文件夹路径、当前运行/暂停状态等）。

### 6.2 任务状态流转

```text
ready ──认领执行──> running ──完成──> succeeded
  │                   ├──失败──> failed（允许直接重试）
  │                   └──取消──> cancelled
  └──取消──> cancelled
```

* 状态流转简单直接：启动即 `running`，完成即 `succeeded`，异常即 `failed`。需要重试时直接重置为 `ready`。服务重启时直接将未完成的 `running` 任务恢复为 `ready`。

## 7. 角色划分、背景同步与记忆维护架构

由于同一平台内不按联系人隔离会话，且存在多个子代理（各平台私信、各平台评论、创作发布），**如何让主会话与所有子代理保持实时一致的背景认知，并在长期运行中高效维护记忆**是系统的核心设计：

### 7.1 角色与会话划分

1. **主会话（Main Session）**：用户交流与全局统筹中枢。定时或被事件唤醒后，根据未处理事件与 `skill` 自主决策（回复转告、整理记忆、同步背景、发起创作或安排发布）。
2. **平台互动工作者（每平台 2 个：私信聊天工作者 + 评论回复工作者）**：
   * 每个平台独立维护一个**私信会话**和一个**评论会话**（如 B 站私信、B 站评论、抖音私信、抖音评论），会话内不拆分单个联系人，按消息队列依次处理。
   * 这种双会话拆分既保留了同一平台内上下文的连贯性（比如评论区大家在聊同一个作品或热点），又避免了评论刷屏把私信上下文冲刷掉或阻塞私信秒回。
3. **媒体与创作/发布工作者**：
   * **媒体工作者**：实现完整工作流接口，当前暂不开启视频抽帧。
   * **创作与发布工作者**：完整实现两种模式——一是扫描并读取**创作文件夹**中用户指定的素材与内容进行发布；二是由人格自主构思创作并在控制台额度内直接发布。

### 7.2 主/子代理双向背景同步（实现一致人格）

为了避免“主会话刚和用户聊完某件事，平台子代理却完全不知道，表现得像另一个机器人”，系统完整实现**“主会话主动推送（Push）+ 子代理主动获取（Pull）”**的双向机制：

1. **主会话主动告诉子代理（Push 机制）**：
   * **更新全局近期背景看板**：当主会话与用户沟通确定了新的近况、心情、观点、近期计划或刚发布了新作品时，主会话直接更新共享的《近期背景看板（Active Context）》。
   * **直接向子代理发信/注入提示**：对于需要各平台立刻知晓的重要背景（例如“今天刚发了关于 X 的新动态，大家来问时可以多聊聊幕后故事”或“最近几天在忙 Y”），主会话可直接通过子代理通信接口或系统事件向各平台的私信/评论工作者发送一条背景通知，直接融入子代理当前会话上下文。
2. **子代理自己主动获取背景（Pull 机制）**：
   * **默认挂载近期看板**：任何子代理（私信、评论、创作）在每轮被唤醒处理任务时，执行适配器自动将《核心人格基线》与最新的《近期背景看板》挂载到系统提示词中，确保子代理天然知道“我是谁、我最近在干嘛、刚发了什么作品”。
   * **按需自主检索记忆工具**：当私信或评论区用户提到过往某个梗、某次经历、某个老熟人（通过消息中附带的发送者昵称/ID 识别）或某篇旧作品时，子代理拥有完全权限，可主动调用记忆查询工具（`search_memory` / `get_acquaintance` / `get_recent_context`）去共享记忆库中调取相关背景，组织出符合一致人设与真实经历的回复。

### 7.3 记忆维护机制（解决膨胀、碎片化与遗忘问题）

针对不隔离联系人、多代理高频互动带来的记忆膨胀与维护难题，完整实现**“三层记忆结构 + 子代理随手记 + 主会话定期蒸馏”**机制：

1. **三层记忆存储结构**：
   * **L1 核心人格层（Core Persona，常驻挂载）**：存放固定人设、性格语气、核心关系与基本设定。体积精简稳定，仅由用户或主会话修改，保证无论运行多久人格底色不变。
   * **L2 近期背景看板（Active Context，常驻挂载 + 高频更新）**：存放“当前状态、最近 3~7 天的重要事件、最新发布的 3~5 个作品摘要、主会话下达的当前焦点背景”。控制在固定字数以内（如 1000~2000 字），所有子代理每次调用自动带上，实现零延迟的全局状态一致。
   * **L3 经历与熟人档案库（Episodic & Acquaintance Store，按需检索）**：
     * **共同经历库**：按时间与主题记录发生过的趣事、创作历程、平台热点互动。
     * **熟人/常客印象卡**：虽然私信和评论会话不按联系人拆分，但为了记住高频互动的粉丝或朋友，子代理在遇到值得记住的互动对象时，可在 L3 中以 `(平台, 用户ID/昵称)` 为索引写入或更新简短的“熟人印象标签”（如称呼偏好、聊过的关键话题）。下次该用户再来私信或评论时，适配器或子代理直接附带/查询该印象卡即可瞬间认出对方。
2. **记忆的写入与定期维护闭环（防膨胀与去噪）**：
   * **子代理轻量记录（Scratchpad 流水）**：私信、评论和创作子代理在日常工作中遇到值得记录的互动、新梗、熟人信息或新发布作品时，随时调用 `add_scratchpad_note` 工具写入待整理记忆流水，不阻塞当前回复速度。
   * **主会话定期蒸馏与修剪（Memory Compaction Skill）**：主会话在定时唤醒（优先级 40）时，执行记忆维护 `skill`：
     1. 读取子代理积累的记忆流水；
     2. 提炼出有长期价值的共同经历与熟人印象，归档进 **L3 经历与熟人库**；
     3. 更新 **L2 近期背景看板**，换下过期状态，保持看板鲜活精炼；
     4. 清空已处理的琐碎流水，彻底解决记忆无限堆积与前后矛盾的问题。
   * **会话压缩无损恢复**：当某个平台的私信或评论会话因为聊得太久触发 DSH 上下文压缩或会话重建时，由于关键状态已在 L2、熟人印象与经历已在 L3，新会话或压缩后会话只需挂载 `L1 + L2` 并配合 L3 检索，即可做到“会话虽重置，记忆不断片”。

## 8. 权限与控制台配置

采用**“控制台集中配置 + 代理最大执行自由”**模式：

* **控制台全权配置**：所有授权策略、管理员 ID、启用平台、发布配额、定时频率、创作文件夹路径均写在控制台，用户可随时查看与改写。
* **默认充分授权**：只要控制台开启对应平台或功能开关，代理即可自主收发私信、回复评论、读写全部记忆、获取全局背景及在额度内直接创作发布。
* **API 与工具自由调用**：迁移或接入各类模型 API、平台插件、`dsh-subagent-library` 与本地工具时无需审核批准，直接赋予完整调用权限。

## 9. DSH 接入要点

1. 在独立运行目录中配置 DSH，打通主会话、各平台私信会话、各平台评论会话、媒体会话与创作发布会话的完整创建、续聊与唤醒接口。
2. 实现完整的上下文装配器与记忆工具集：在调用 DSH 前自动拼装 `L1 核心人格 + L2 近期背景看板 + 发送者熟人印象卡（若有）`，并向主/子代理暴露全套记忆读写、背景广播、跨会话转告与任务委派工具。
3. 编写完整的 `skill` 集合：涵盖主会话自主统筹、记忆蒸馏维护、私信秒回互动、评论区互动、创作文件夹发布与自主创作。

## 10. 阶段推进（全量接口按序落地，每步完整跑通）

**重要原则：不做阉割版“最小成功样例（Toy Demo）”。** 按照 M1 → M5 的顺序，每一步都把该模块涉及的**全部数据库表、全部函数接口（含预留接口）和完整业务逻辑一次性写好并跑通**，避免后续反复推翻重构：

### M1 — 全量存储与调度内核落地
1. 一次性建好 SQLite 全部核心表（`events`、`timers`、`jobs`、`actors`、`memories`、`actions`、`config`）及完整的读写接口。
2. 完整实现事件去重入库、一次性/周期性定时器触发、按平台双通道（私信/评论分离）与各业务工作者的优先级队列调度、状态流转（`ready/running/succeeded/failed/cancelled`）、暂停/恢复、重启恢复及耗时统计接口，并逐一验证跑通。

### M2 — 三层记忆中心与双向背景同步全量落地
1. 完整实现 `L1 核心人格`、`L2 近期背景看板`、`L3 共同经历与熟人印象卡` 以及 `Scratchpad 记忆流水` 的全套存储、检索、更新与归档清理接口。
2. 完整实现上下文装配器（自动组装 L1 + L2 + 熟人印象卡）以及供主/子代理调用的全套记忆工具与 Push/Pull 背景同步接口、管理员 ID 核验与跨会话持久化转告接口，并全部跑通。

### M3 — DSH 执行适配器、多角色会话与全套 Skill 落地
1. 完整实现 DSH 执行适配器，打通 `main`、`bili_chat`、`bili_comment`、`douyin_chat`、`douyin_comment`、`xhs_chat/comment（预留）`、`media（预留）`、`creator`、`publisher` 全部角色的会话映射、创建、续聊、唤醒与工具挂载。
2. 编写并落地主会话统筹、记忆蒸馏、私信聊天、评论回复、自主创作发布的全套 `skill`，跑通主/子代理协同与记忆蒸馏闭环。

### M4 — 平台适配器体系、创作文件夹与自主发布全量落地
1. 定义并实现统一的平台适配器标准接口（收发私信、读写评论、提及监听、发布内容、视频帧预留接口），完整实现 B 站与抖音适配器骨架与通信闭环，建好小红书与媒体抽帧标准接口桩。
2. 完整实现**创作文件夹**扫描读取、配额核算、自主创作与对外发布流程，跑通从平台监听、2 分钟内私信秒回、评论回复到作品发布的完整业务流。

### M5 — 控制台与展示性工作台全量落地
1. 实现完整的后端 API 与可视化控制台/展示工作台前端界面。
2. 跑通在工作台中实时查看/修改管理员 ID、平台开关、发布配额、创作文件夹路径，以及实时观测任务队列、各平台会话动态、发送记录和在线查看/编辑 L1/L2/L3 记忆看板的全部功能。

## 11. 可随时调整的事项

* 项目名称、展示工作台 UI 细节、具体选用的开源插件与底层模型，可在完整接口之上自由配置与替换。
* 小红书与视频抽帧的统一接口在 M1~M4 中先行完整定义并接好调用链路，待后续开启时直接填入平台具体实现即可，无需改动调度器与工作台架构。
